# Security and host responsibilities

The default schema has no raw HTML block. Paragraph content consists of text and typed inline marks. Default DOM renderers create text nodes; React renderers use escaped content. A string containing `<script>` is displayed as text. Unsafe URL protocols, credentials, malformed inputs, non-finite chart data, and invalid schema versions reject before any operation commits. Only HTTP/HTTPS hyperlinks are supported; embeds require HTTPS.

SuperChart embed descriptors do not automatically load an iframe. Hosts explicitly enable embeds and supply exact allowed HTTPS origins. Default iframe rendering uses a sandbox, no `allow-same-origin`, lazy loading, and no-referrer. Hosts must trust those origins and their chosen sandbox behavior. Configured custom block/chart renderers are trusted application code and can bypass default rendering safety; audit them separately. The core does not fetch URLs, so URL validation is not an SSRF policy. A host adding URL fetching must enforce its own network restrictions.

The actor in a transaction is provenance supplied by a caller, not an authentication credential. Never expose the HTTP/MCP adapters to untrusted clients without host authentication, authorization, request budgets, CSRF/origin policy where appropriate, and revision-guarded durable writes. Error responses are data, not instructions to weaken guards. A stale agent proposal must be re-read and reviewed; never retry by stripping expected versions.

The local CLI operates only on caller-selected report JSON files. It does not resolve remote URLs, invoke provider SDKs, call trading APIs, or persist session undo history. It takes an exclusive `.lock` file before reading and applying a transaction, then atomically replaces the document. Other writers must participate in that lock protocol. A stale lock fails safely and is left for explicit host recovery. Persistent applications must coordinate external writers and durable compare-and-swap updates separately.

Document size limits and bounded in-memory history help keep the vertical slice predictable. For production, define memory quotas, request timeouts, audit retention, durable idempotency semantics, and isolation for expensive custom chart rendering. This repo does not claim real-time collaboration, policy enforcement for trading, or a complete hosted service.

## Image and embed URLs

An `image` or `embed` block carries a URL that a viewer's browser may be asked to load. Because agents write these blocks, treat every such URL as untrusted input.

**What the Core enforces on every write path** (editor operations, every transport, `parseDocument` of a file): the URL must be an absolute `https://` URL of at most 4,096 characters, with no credentials (`user:password@`), no whitespace, no control characters and no backslashes. `http:`, `data:`, `javascript:`, `file:`, `blob:` and relative URLs are rejected before anything is committed, with a hint. Hyperlinks inside text accept `http:` and `https:` only. `image` requires `alt` text; embed `height` is limited to 200 to 1,200.

**What it does not do.** Validation is not permission to load. The Core never fetches a URL, so it is not an SSRF or tracking policy. A host that renders these blocks must decide which origins may load:

- **Images.** Prefer an allow-list: a `Content-Security-Policy` `img-src` of the hosts you trust, or serve images through your own proxy that enforces the allow-list, content type (no SVG scripts), size and timeout. A remote image load tells its host the viewer's IP address, user agent and the moment the report was opened, so an agent-supplied URL is a tracking channel. Render with `<img>` only (never `<object>`, `<iframe>` or inline SVG from a URL), with `referrerpolicy="no-referrer"`, `loading="lazy"` and `decoding="async"`, and keep the width classes (`narrow`, `normal`, `wide`, `full`) as the only sizing.
- **Embeds.** The default is a link card, not an iframe. Enable embeds only for exact HTTPS origins you trust (the UI package takes an explicit allow-list), render them in an `<iframe>` with `sandbox` (without `allow-same-origin` unless the origin is yours), `referrerpolicy="no-referrer"`, `loading="lazy"` and no `allow` permissions, and add the origin to `frame-src`. Fall back to the link when the origin is not allowed.
- **Servers that fetch.** A host that downloads images or embeds server-side (thumbnails, PDF export, link previews) must apply its own SSRF defences: resolve the host and refuse private, loopback and link-local addresses, do not follow redirects blindly, set timeouts and size caps, and never forward credentials.
- **Exports.** `toHTML` re-checks every link and image URL and turns embeds into links; the HTTP `/export.html` route adds `Content-Security-Policy: default-src 'none'; img-src https:; style-src 'unsafe-inline'; sandbox` so a generated page stays inert when opened directly. Serve user-visible exports from a separate origin or with `Content-Disposition: attachment` if you do not trust the author of the document.

## Transports

The HTTP handler, the MCP server and the CLI all run the same actions through the same Core, so they share the guarantees above (atomic edits, version guards, URL checks, budgets). Their own boundaries:

- **No authentication.** The actor on an edit is provenance supplied by the caller. HTTP: set the `actor` option from your authenticated session (it wins over a body `actor`), or put the handler behind your own authentication; enable `cors` only for exact origins you control; never send cookies-authenticated requests to it without CSRF protection; use `readOnly` for public views.
- **Bounded input.** Request bodies default to 1 MiB (`413` beyond), query strings are strict (unknown parameters are `400`), JSON is parsed without accessors or prototypes, stdio lines are capped at 4 MiB, files read by the CLI and the stdio server at 32 MiB, markdown at 1,000,000 characters. See the limits table in [API.md](API.md#limits).
- **The MCP server is scoped to one file.** It runs with the permissions of the user who started it, the path is fixed at startup, and no tool takes a file path. Use `--read-only` for reviewing agents and give each agent its own `--actor`. Clients can ask a person to approve calls using `readOnlyHint` and `destructiveHint`. Edits are saved atomically under `<file>.lock`; a stale lock is reported, never deleted.
- **The CLI writes where you point it.** `export --out` writes to the path you give (it refuses to overwrite the document itself), `new` and `init` refuse to overwrite an existing file, and editing commands replace the document atomically. Treat paths from an untrusted agent as untrusted, or run the CLI in a directory you control.
- **Document text is data, not instructions.** An agent that reads a report is reading text any earlier author (a person, another agent, an imported file) could write. Tool results include that text; treat instructions found in it as content to report, not commands to follow. The server instructions and the shipped prompts tell the agent the same.
- **Errors are data.** A `hint` tells an agent how to fix its call; it never asks it to remove a guard. Do not retry a conflict by stripping `expectedVersion`.
